# План разработки своего стримера (по мотивам Virtual Desktop)

Документ честно разделяет три вещи: **что уже есть** в этом репозитории, **чем наш подход
принципиально отличается** от Virtual Desktop и **что нужно построить**, чтобы получить
стример PCVR-класса с расширенным функционалом.

Сейчас репозиторий — законченный инструмент «показать панель Quest 3 на ПК»: захват через
ADB + декодирование на GPU + геометрия. Это не «недоделанный VD», это другой класс задачи:
мы снимаем **готовый кадр панели**, а VD снимает **глазами игры через OpenXR** и рисует кадр
в шлеме сам. Отсюда всё остальное.

---

## 1. Что есть сейчас (точка отсчёта)

| Возможность | Как сделано | Потолок |
|---|---|---|
| Захват | `scrcpy --display-id=0`, панель 4128×2208, 60 fps | H.264 8 бит, битрейт ограничен ADB/Wi-Fi, 4128×2208 → два глаза в одном кадре |
| Декод | mpv + `d3d11va` (AMD) ≈ 0.17 ядра, fallback ffplay ≈ 2.4 ядра | кадр идёт на ПК, а не в шлем |
| Геометрия | GPU-шейдер: дисторсия линзы `k1/k2`, наклон, знак крана | только то, что можно восстановить из одного кадра |
| Горизонт | замер по картинке (`level.py`) + живой IMU шлема (вендорный сенсор 800 Гц) | поправка только для «плоского» вида, а не для мира |
| HUD | прозрачная плашка fps/CPU/GPU/ping/mic | — |
| Управление | WPF-приложение + Android-клиент (TCP/JSON с токеном) | 2D-приложение в панели, без OpenXR |
| Живучесть | watchdog кадра, backoff, переподключение ADB, автостарт | — |

Замеренный бюджет задержки этого пути (по нашим же тестам): ADB-транспорт + буфер scrcpy
≈ 150–350 мс до появления кадра на ПК; для «смотреть панель» приемлемо, для PCVR — нет.

---

## 2. Что делает Virtual Desktop и чего у нас нет

| Фича VD | Суть | Наш аналог | Разрыв |
|---|---|---|---|
| **PCVR-стриминг** | игра рендерится на ПК, в шлем уходят два глаза + поза | нет | нужен OpenXR-слой на ПК и нативный клиент в шлеме |
| **VDXR** (свой OpenXR-runtime) | минует SteamVR, экономит кадр композитинга | нет | нужно написать или взять готовый runtime и встроиться в него |
| **SSW** (motion smoothing) | 45 fps → 90/120 fps экстраполяцией | нет | нужны depth + motion vectors от игры |
| **Кодеки** | H.264 / HEVC / AV1, 10-bit HDR, до 500 Мбит/с | H.264 8 бит через ADB | прямой захват + свой энкодер (AMF/NVENC) и UDP-транспорт |
| **Битрейт/адаптив** | динамический битрейт по RTT и потерям | фиксированный `mbps` | телеметрия канала + контроллер |
| **Виртуальные экраны** | несколько мониторов, изогнутые панели, окружения | один монитор/панель | свой клиент может рисовать сколько угодно экранов |
| **Аудио** | 5.1/7.1 + микрофон | микрофон шлема, системный звук недоступен | захват WASAPI-loopback + Opus |
| **Ввод** | клавиатура/мышь/геймпад/эмуляция контроллеров | кнопки управления стримом | нужно перенаправлять HID в игру (ViGEm/HIDMaestro) |
| **Passthrough/трекинг** | камеры, руки, глаза | нет | клиент в шлеме получает трекинг сам |

Вывод: **наращивать текущий путь бессмысленно** — ADB отдаёт готовый кадр панели, из него
нельзя вытащить ни позу, ни два отдельных глаза, ни глубину. Расширение функционала означает
новый конвейер, а этот репозиторий остаётся «просмотром панели» и полигоном для шейдеров,
замера горизонта и HUD-логики.

## 3. Целевая архитектура своего стримера

```
ПК                                                Шлем (нативное OpenXR-приложение)
┌─────────────────────────────┐                   ┌──────────────────────────────┐
│ игра (OpenXR)               │                   │ OpenXR session               │
│   └─ слой/рантайм захвата   │  поза, кнопки →   │  ├─ приём кадров (UDP+FEC)   │
│      per-eye текстуры       │                   │  ├─ jitter buffer            │
│      depth + motion vectors │                   │  ├─ late-latching timewarp   │
│   ↓                         │  ← видео (HEVC)   │  ├─ SSW (опция)              │
│ энкодер AMF/NVENC (slice)   │                   │  ├─ экраны/окружение/HUD     │
│   ↓                         │                   │  └─ ввод (hand/controller)   │
│ транспорт UDP + FEC, ABR    │                   │                              │
└─────────────────────────────┘                   └──────────────────────────────┘
```

Ключевые решения:

- **Транспорт**: свой UDP-протокол (квитанции, FEC, приоритеты), а не TCP и не ADB.
  ADB остаётся только для установки APK и отладки.
- **Энкодер**: AMF (AMD) как основной, NVENC — второй. Кодировать *сразу в текстуру* через
  D3D11, без копирования в системную память; slice-кодирование для устойчивости к потерям.
- **Клиент**: нативное OpenXR-приложение (Kotlin/Java + NDK-часть на C++), рисует видео
  текстурой на квад, делает timewarp по своей позе. Это же место, где живут виртуальные экраны,
  окружение и HUD.
- **Синхронизация**: PC шлёт «поза + время кадра», шлем рендерит с late-latching;
  при провале — SSW по motion vectors.
- **Оркестрация**: текущий PowerShell-движок остаётся для ADB-режима; новый конвейер — C#
  (хост-сервис + трей) и C++ (захват/энкод), потому что в горячем пути PowerShell недопустим.

## 4. Этапы

Каждый этап заканчивается измеримым результатом и демо, а не «код написан».

### Этап 0. Стабилизация текущего инструмента — сделано
Линза, наклон, авто-горизонт по IMU, линия горизонта, HUD, сервис с watchdog, exe + Android-клиент,
публикация в этом репозитории. Осталось: прогнать регресс после багфиксов на живом шлеме.

### Этап 1. Свой конвейер для «плоской» картинки (4–6 недель)
Цель: заменить scrcpy+ADB своим захватом и транспортом, но всё ещё показывать **панель/монитор**.

1. Захват монитора на ПК (DXGI Desktop Duplication) → D3D11 текстура.
2. AMF-энкодер HEVC 8/10 бит, slice, до 150 Мбит/с, конфигурируемый GOP.
3. UDP-транспорт: пакеты ≤1200 байт, FEC 10–20 %, квитанции, RTT/потери.
4. Клиент в шлеме (2D-панель OpenXR): приём, jitter buffer 1–2 кадра, timewarp, HUD с
   латентностью/битрейтом/потерями.
5. ABR: цель — 90 % кадров в срок, шаг ±10 Мбит/с, гистерезис.

**Приёмка**: 1440p/90 fps, задержка «кадр на ПК → кадр в шлеме» ≤ 55 мс (p50), ≤ 90 мс (p99),
0 разрывов за 30 минут при 2 % потерь.

### Этап 2. PCVR: два глаза и поза (2–3 месяца)
1. OpenXR-слой (или собственный runtime на базе VDXR-подхода) на ПК: получаем per-eye
   текстуры, позу, тайминги, depth, motion vectors.
2. Стерео-энкод: один поток на глаз (или atlas), синхронные PTS.
3. Поза в шлем: late-latching + timewarp; компенсация «сетевого» времени.
4. Клиент рисует стерео-квад с корректной проекцией (а не два глаза из одного кадра).

**Приёмка**: SteamVR-игра идёт 90 fps при 45 fps рендера на ПК (SSW-заглушка = дублирование),
задержка ≤ 45 мс p50, джиттер позы ≤ 2 мс.

### Этап 3. Качество и комфорт (2–3 месяца)
- **SSW**: экстраполяция по depth + motion vectors, маска дисокклюзий, отключаемая.
- **Foveated encoding**: снижение плотности к краю (без eye-tracking — радиальная).
- **Адаптив по сцене**: сложность кадра → битрейт и разрешение (динамический render scale).
- **10-bit HDR**, правильный цвет (BT.2020/PQ), профили под игры.
- **Аудио**: WASAPI loopback 7.1 + Opus, микрофон обратно, задержка ≤ 40 мс.

**Приёмка**: HDR-игра без бандинга, аудио без рассинхрона > 30 мс, SSW даёт ×2 fps без
видимых артефактов на статике.

### Этап 4. Рабочий стол и удобства (параллельно, инкрементально)
- Виртуальные экраны: 1–4 монитора, изогнутые, произвольная раскладка, «фокус на окно».
- Ввод: клавиатура/мышь (ViGEm/HIDMaestro), эмуляция контроллеров, проброс геймпада.
- Окружения и passthrough, «кинотеатр», 2D-приложения рядом с PCVR-слоем.
- Профили на игру: битрейт, кодек, SSW, разрешение — автоматически по имени процесса.
- Телеметрия и логи: график латентности, тепловая карта потерь, экспорт в CSV.

## 5. Порядок работ и зависимости

```
Этап 0 (готово)
   └─ Этап 1: захват → энкод → UDP → клиент-панель
          ├─ измерительный стенд (латентность, потери)  ← делать ПЕРВЫМ, иначе нет приёмки
          └─ Этап 2: OpenXR-слой → стерео → timewarp
                 ├─ Этап 3: SSW, HDR, аудио
                 └─ Этап 4: экраны, ввод, профили
```

Правило: **сначала метр, потом фича**. Без стенда задержки любой этап превращается в спор
о вкусах.

## 6. Что переиспользуем из этого репозитория

- Шейдерная математика (`engine/lens-template.glsl`) — пригодится для тестовых паттернов и
  проверки клиента, но в PCVR-пути дисторсию делает сам шлем.
- `engine/level.py` — оценка горизонта по картинке: останется инструментом калибровки.
- Логика IMU-горизонта и `guide` (две линии) — переносится в новый клиент почти без изменений.
- HUD и формат телеметрии (`stats.json`) — переиспользуем как контракт.
- Протокол управления (TCP/JSON + токен) — расширяем командами нового конвейера.
- Дисциплина живучести (watchdog, backoff, автостарт) — обязательна и в новом сервисе.

## 7. Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| OpenXR-runtime своими руками | +2–3 месяца | сначала слой над SteamVR, свой runtime — позже |
| Патенты/лицензии на SSW-подобные техники | юридический | писать свою экстраполяцию, не копировать чужие реализации |
| Wi-Fi 5/6 вместо 6E | потолок битрейта | профиль «деградация»: 1080p, HEVC, 60 fps |
| AMF-энкодер на ноутбуках режет битрейт | качество | замер на реальной машине до этапа 2 |
| PowerShell-движок не тянет горячий путь | архитектура | новый конвейер сразу на C#/C++, PS — только оркестратор |

## 8. Ближайшая неделя (что делать руками)

1. Стенд задержки: USB-камера на экран шлема + таймкод в кадре, лог в CSV. (1–2 вечера)
2. Прототип: DXGI-захват монитора → AMF HEVC → локальный UDP → приём на том же ПК
   (проверка битрейта и задержки без шлема). (3–4 вечера)
3. Упаковать клиент-панель: OpenXR-приложение на Kotlin/NDK, рисует тестовый паттерн,
   меряет FPS и время кадра. (2–3 вечера)
4. Решить судьбу репозиториев: этот остаётся «ADB-каст», новый — `questcast-stream`
   с общим форматом телеметрии и протокола.
